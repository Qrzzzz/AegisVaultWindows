# AegisVault 2.4 — closed text and file-output boundaries

Released 2026-09-05.

## Changes

- Text input now uses a shared packaged contract across WinUI, UTF-8 import, Use Result, JSON Lines and the Python
  backend. Plaintext is bounded at 1,507,294 UTF-8 bytes/code units; encoded text remains bounded at 2 MiB; every
  successfully generated text result fits the reverse workflow. Request and response lines remain capped at 16 MiB.
- Reverse Base64 and AGV1 operations reject decoded plaintext outside the forward budget. AGV1 size is checked from
  the envelope before scrypt, while valid ASCII, multibyte BMP and non-BMP Unicode retain complete roundtrips.
- Collision numbers for `.agv` and `.b64` wrappers are inserted before the original logical extension chain:
  `report.txt.agv`, `report (1).txt.agv`, `report (2).txt.agv`. Restoring the numbered wrappers therefore produces
  `report (1).txt` and `report (2).txt` with byte-identical contents.
- Atomic writers use a fixed 40-character, CSPRNG-derived sibling temp component created with exclusive OS flags.
  The internal name no longer contains the target name, while flush, same-filesystem publication, overwrite,
  no-overwrite, race handling and cleanup retain their prior platform-specific semantics.

## Compatibility

AGV1 protocol version 1, AES-256-GCM, scrypt parameters, file payloads, Base64 behavior, settings schema, bilingual
UI and the 2.2/2.3 transaction and process-lifecycle contracts are unchanged. Existing `AGV1.` tokens and `.agv`
files remain compatible. The only intentionally narrower behavior is rejection of text that cannot participate in
a bounded forward-and-reverse application workflow.

Release artifact names are `AegisVault-v2.4-win64.zip` and `AegisVault-v2.4.cdx.json`; Windows PE and assembly
versions are `2.4.0.0`. See [local 2.4 acceptance](../ACCEPTANCE_2.4.md) for executed and pending gates.
