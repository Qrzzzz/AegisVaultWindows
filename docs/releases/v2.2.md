# AegisVault 2.2 — Base64 input checks and settings transactions

This release addresses issues
[#9](https://github.com/Qrzzzz/AegisVaultWindows/issues/9),
[#10](https://github.com/Qrzzzz/AegisVaultWindows/issues/10) and
[#11](https://github.com/Qrzzzz/AegisVaultWindows/issues/11).

- Base64 file encoding and decoding bind the initial size and metadata to the opened input handle,
  count bytes read and check for detectable changes before publishing. Changed input reports
  `file.input_changed` and rolls back temporary output. Streaming, cancellation and atomic
  no-overwrite publication remain in place; metadata checks do not provide a strict concurrent snapshot.
- Settings JSON with an integer beyond Python's digit limit now follows the existing bad-configuration
  fallback. Settings reads, updates and ordinary operations remain available without changing the
  interpreter's integer safety limit or swallowing model/programming errors.
- Settings updates and recent-history changes lock the entire read-modify-save transaction across
  cooperating processes. Lock contention expires after five seconds with `settings.lock_timeout`;
  lock access failures report `settings.lock_failed`. Both have Chinese and English UI messages.
  Waiting observes cancellation; normal exceptions and process exit release the operating-system lock.

Configuration fields, including `show_advanced_options`, remain compatible. The empty persistent
`.settings.json.lock` sidecar is an identity for the operating-system lock, not a stale-lock marker;
do not remove it while application instances are running. Older versions and external editors do not
participate in this lock. Crypto operations do not hold it.

The backend merges request fields into the latest persisted settings while locked. The current WinUI
Save action explicitly sends all six preference fields: two windows saving old drafts still use
last-writer-wins for those submitted fields. This version does not add client conflict detection.

AGV1 format, AES-256-GCM, scrypt, the WinUI layout, dependency locks and protocol version remain unchanged.
IPC lifecycle work is reserved for 2.3; text budgets and output-name repairs are reserved for 2.4.

Download `AegisVault-v2.2-win64.zip` and extract the entire folder before running `AegisVault.exe`.
The release also includes `AegisVault-v2.2.cdx.json` and `SHA256SUMS`, with GitHub build provenance
for all three assets. Windows PE/assembly versions are `2.2.0.0`.

Local validation passed 301 Python tests, static/version checks and actual WinUI interaction in
light/en-US and dark/zh-CN, including the new settings lock errors and successful retry.
See [2.2 local acceptance](https://github.com/Qrzzzz/AegisVaultWindows/blob/v2.2/docs/ACCEPTANCE_2.2.md) for measured results and remaining manual-test limits.
Authenticode signing depends on the configured signing mode; build provenance does not imply a code-signing certificate.
