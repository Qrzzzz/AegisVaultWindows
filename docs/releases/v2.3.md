# AegisVault 2.3 — bounded backend lifecycle

Version 2.3 hardens the local backend lifecycle while preserving the WinUI and AGV1 compatibility contracts.

## Changes

- Backend cancellation supervision begins before the first potentially blocking stdin write. The UI callback
  only signals cancellation; a background notification attempts cooperative cancellation while an independent
  30-second guard can terminate the exact process tree created for the call.
- `hello`, settings and recent-history requests have a 15-second end-to-end response deadline. Text and file
  operations retain no fixed total deadline. Terminal-process exit is allowed five seconds before forced
  reaping, followed by a five-second reap boundary.
- Window initialization and independent settings operations can be cancelled on close. Settings `IsBusy` and
  `ActiveTask` settle after result, failure, cancellation or timeout. A committed file result survives a
  subsequent recent-history timeout or cancellation and is accompanied by a warning.
- The backend rejects request IDs containing isolated Unicode surrogates before dispatch and before settings
  side effects. Valid Unicode, including non-BMP characters, remains supported.
- The client validates protocol version, progress-byte and file-size values as correctly typed, in-range JSON
  integers. Fault-injected fractional, overflowing and wrongly typed numbers map to `ipc.invalid_response`.

## Compatibility

The AGV1 text and file formats, scrypt/AES-256-GCM behavior, atomic no-overwrite writes, streaming file paths,
bilingual UI, accessibility contracts and all settings fields—including `show_advanced_options`—are unchanged.
The transactional settings lock introduced in 2.2 remains in use, including its cancellation token and
five-second lock-acquisition deadline.

Release artifact names are `AegisVault-v2.3-win64.zip` and `AegisVault-v2.3.cdx.json`; Windows PE and assembly
versions are `2.3.0.0`.
See [local 2.3 acceptance](../ACCEPTANCE_2.3.md) for executed evidence and remaining gates.
